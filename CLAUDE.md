# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Reusable GitHub Actions workflows and composite actions for R packages in the shiny-verse. It is internal to the Shiny team; sweeping changes are made without notice. There is no build system, test suite, or linter — everything is YAML (workflow/action definitions) with inline bash and R scripts. Changes are validated by consuming repos running the workflows.

## Architecture

Two layers, plus internal helpers:

1. **Reusable workflows** (`.github/workflows/`, invoked via `workflow_call` from consumer repos as `rstudio/shiny-workflows/.github/workflows/<name>.yaml@v1`):
   - `R-CMD-check.yaml` — matrix R CMD check across macOS/Windows/Ubuntu and multiple R versions (matrix config is generated by an inline script). Includes an optional depends-only check job.
   - `routine.yaml` — housekeeping that commits results back to the consumer repo: air formatting, `usethis::use_tidy_description()`, `devtools::document()`, `build_readme()`, covr, lintr, npm/yarn build+test, staticimports check.
   - `website.yaml` — pkgdown build and deploy to `gh-pages`.
   - `lock-threads.yaml` — locks inactive issues/PRs (consumer copies `examples/lock-threads.yaml`).

2. **Composite actions** (top-level directories, invoked as `rstudio/shiny-workflows/<dir>@v1`):
   - `setup-r-package/` — the "go-to" setup: installs pandoc, R, OS system deps, package deps; chains into `setup-phantomjs` and `setup-tinytex`.
   - `setup-phantomjs/`, `setup-tinytex/` — conditional installs, only when `shinytest`/`webdriver` or `tinytex` are direct DESCRIPTION dependencies. Meant to be called via `setup-r-package`, not directly.
   - `setup-macOS-dependencies/` — brew installs for known R package system deps.
   - `format-r-code/` — installs and runs the air formatter (check mode or format-and-commit mode).

3. **Internal composite actions** (`.github/internal/`, used only by the reusable workflows): `checkout` (auto git-LFS detection), `setup-git` (git user config), `run-local-script` (runs consumer's `.github/shiny-workflows/<name>.R|.sh` hook scripts), `verify-no-new-commits` (fails if auto-generated commits exist), `verify-pkgdown`.

**Consumer hook scripts**: consumer repos can drop `package-install`, `website`, or `routine` scripts (`.R` or `.sh`) into their `.github/shiny-workflows/` folder; the workflows run them at defined points via `run-local-script`.

## Releasing changes

Workflows are consumed via the `v1` tag. Until the tag moves, consumers on `@v1` do not see merged changes — merging a PR ships nothing on its own.

**After a PR is merged to `main`, use the `update-v1-tag` skill** (`.claude/skills/update-v1-tag/SKILL.md`) to move the tag. Do not run the tag commands from memory: the skill carries the pre-flight checks, tags `origin/main` explicitly (bare `git tag -f v1` tags `HEAD`, which is wrong whenever you are not sitting on the merge commit), stops for explicit user confirmation before the force-push, and records a rollback point.

When testing changes from a consumer repo, reference the branch instead (`@<branch-name>`).

## Conventions

- Cross-references between workflows and actions use `@v1` (e.g., `routine.yaml` calls `rstudio/shiny-workflows/setup-r-package@v1`), so in-flight changes to an action aren't picked up by a workflow in the same branch unless those refs are temporarily pointed at the branch.
- README.md documents all workflow/action parameters; keep it in sync when adding or changing inputs (past commits do this, e.g. "docs: Update documentation with missing workflow and action parameters").
- Each action directory has its own README with an inputs table — update it alongside `action.yaml`.
- **Adding an R package to a system-dependency list means adding it to the test fixture.** If you add an entry to `brew_list` in `setup-macOS-dependencies/action.yaml` (or any equivalent per-package system setup), add that package to `Suggests:` in `.github/fixtures/macosdeps/DESCRIPTION` and to the `pkgs` vector in that fixture's `tests/deps.R`. The fixture is what `.github/workflows/test-integration.yaml` checks, and it is the only thing standing between a stale list and a silent break. Note the fixture *loads* each package rather than only installing it: a binary linked against a missing system library installs cleanly and fails at `dlopen`, which is exactly how the `Cairo`/XQuartz case was found. Removing an entry from a list means removing it from the fixture only if the package is genuinely unreachable (e.g. archived from CRAN) — otherwise leave it in, so the fixture keeps proving the entry is unnecessary.
- Feature policy (from README): adopt a feature if 2+ repos need it or all repos could benefit (e.g., phantomJS, tinytex auto-install); reject features that appease a single repo or impose behavior other repos won't adopt.

## Example workflows (`examples/`)

`examples/` holds the copy-into-your-repo caller workflows for consumer repos: `pkg-r.yaml` (all three workflows in one, the default) plus per-workflow files (`R-CMD-check.yaml`, `routine.yaml`, `website.yaml`) and `lock-threads.yaml`. Every reusable workflow in `.github/workflows/` should have a corresponding example file here.

When adding or editing an example:

- **Every example gets `workflow_dispatch:`.** Consumers need to trigger these by hand from the Actions tab. In particular, never add `repository_dispatch` without also adding `workflow_dispatch` — a workflow that can be triggered by another repo but not by a human in this one is a debugging dead end.
- Give `repository_dispatch` an explicit `types:` list (e.g. `repository_dispatch: { types: [website] }`) so that unrelated dispatches don't fire it.
- Reference the reusable workflow at `@v1`, matching the rest of the repo.
- Open with the `# Workflow derived from https://github.com/rstudio/shiny-workflows` header comment, and — for any file that splits a job out of `Package checks` — a `NOTE:` telling the consumer to remove that job from their `pkg-r.yaml`.
- Do not add a `schedule:` trigger. Consumer repos decide their own cadence; the only example that is schedule-driven is `lock-threads.yaml`, where the schedule *is* the feature.
- Set a `concurrency:` group. Cancel superseded pull request runs, but do not cancel `routine` (it pushes commits back and a run cancelled mid-push is worse than a redundant run) and do not cancel `website` pushes (two deploys must not race on `gh-pages`).
- Document the new file in `examples/README.md` with a `usethis::use_github_action(url = ...)` snippet, and link it from the matching workflow bullet in the top-level `README.md`.
