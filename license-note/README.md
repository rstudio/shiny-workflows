# license-note

## Keep `LICENSE.note` in sync with bundled JavaScript dependencies

If your R package bundles third-party JavaScript, CRAN expects a `LICENSE.note`
file that "describes the overall license of the package, and the specific
licenses of each individual component"
([R Packages, "Code you bundle"](https://r-pkgs.org/license.html#sec-code-you-bundle)).
Keeping that list current by hand is easy to forget.

This action reads the direct dependencies (`dependencies` in `package.json`) out
of the installed `node_modules` and rewrites the list of components in
`LICENSE.note`, either committing the result or failing when it is out of date.

## Opting in

The action only rewrites the region between two marker lines, so the rest of
`LICENSE.note` — the summary paragraph, and any components that do not come from
npm — stays under your control. A repo opts in by adding the markers once:

```
The example package as a whole is distributed under MIT. The example package
includes other open source software components. The following is a list of
these components:

### BEGIN bundled JavaScript dependencies (generated by rstudio/shiny-workflows)
### END bundled JavaScript dependencies

Full copies of the license agreements used by these components are included in
`inst/lib`.
```

After the action runs, the block is filled in:

```
### BEGIN bundled JavaScript dependencies (generated by rstudio/shiny-workflows)

* bootstrap@5.3.3: MIT (https://github.com/twbs/bootstrap)
* jquery@3.7.1: MIT (https://github.com/jquery/jquery)

### END bundled JavaScript dependencies
```

If `LICENSE.note` does not exist, or exists but has no `BEGIN` marker, the
action logs a notice and does nothing. Nothing outside the markers is ever
touched.

## Choosing which packages are listed

By default the action lists the direct `dependencies` from `package.json`.

That default is wrong for most shiny-verse repos. The
`dependencies`/`devDependencies` split describes *build* roles, not what is
shipped: `{bslib}` has no `dependencies` at all and bundles from
`devDependencies`, and `{shiny}`'s `dependencies` are mostly `@types/*` packages
that ship nothing while the libraries it actually bundles (`jquery`,
`bootstrap-datepicker`, `@selectize/selectize`) sit in `devDependencies`.

Only the repo knows what its bundler inlines, so name the bundled packages
explicitly in `package.json`:

```json
{
  "licenseNote": {
    "bundled": ["jquery", "bootstrap-datepicker", "@selectize/selectize"]
  }
}
```

When `licenseNote.bundled` is present it replaces the default entirely, and the
listed packages may come from either dependency group.

Bundled code that does not come from npm at all — vendored files checked into
`inst/`, code taken from R itself — cannot be detected. List it by hand outside
the markers.

Note that `LICENSE.note` is only half of the job: copyright holders of bundled
code should also be listed in `DESCRIPTION` with `role = "cph"`. See
[`{diffviewer}`](https://github.com/r-lib/diffviewer) for a package that does
both.

## Inputs

| Input                | Description                                                                   | Default          | Required |
|----------------------|-------------------------------------------------------------------------------|------------------|----------|
| path                 | Path to the license note file, relative to `working-directory`                 | `'LICENSE.note'` | No       |
| check                | If `'true'`, only check that the license note is up to date                    | `'false'`        | No       |
| working-directory    | Directory containing the license note file, relative to the repository root    | `'.'`            | No       |
| js-working-directory | Directory containing `package.json`, relative to the repository root           | `working-directory` | No    |
| comment              | If `'true'`, comment on the pull request when the license note changes         | `'true'`         | No       |
| token                | Token used to write the pull request comment                                   | `github.token`   | No       |

`working-directory` and `js-working-directory` are both relative to the
repository root, matching how `routine.yaml` uses them; `path` is relative to
`working-directory`. The two may differ — an R package in `pkg/` whose
JavaScript sources live in `pkg/js/` sets `working-directory: pkg` and
`js-working-directory: pkg/js`, and the generated block lands in
`pkg/LICENSE.note`.

Packages are resolved from `js-working-directory/node_modules`, falling back to
a hoisted `node_modules` further up (a monorepo root, or the package directory
when `js-working-directory` is nested inside it). The search stops at the
repository root, so nothing outside the checkout can be picked up.

## Usage

The dependencies must already be installed — the license of each dependency is
read from its installed `package.json` — so run this after `npm ci` / `yarn
install`:

```yaml
- name: Install JS dependencies
  run: npm ci

- name: Update `LICENSE.note`
  uses: rstudio/shiny-workflows/license-note@v1
```

Like `format-r-code`, this action commits its changes back to the repository, so
configure your git user first:

```yaml
- name: Configure git
  run: |
    git config --global user.name "$GITHUB_ACTOR"
    git config --global user.email "$GITHUB_ACTOR@users.noreply.github.com"
```

To fail the workflow when `LICENSE.note` is out of date instead of committing
the fix, set `check: true`:

```yaml
- name: Check `LICENSE.note`
  uses: rstudio/shiny-workflows/license-note@v1
  with:
    check: true
```

## Pull request comment

When the note changes during a `pull_request` run, the action leaves a comment
saying so and pointing at `licenseNote.bundled`, because a change to what this
package redistributes should get a human's attention rather than sliding by as
one more auto-generated commit.

The comment is keyed by a hidden marker and edited in place, so a PR that
triggers several runs ends up with one comment, not a pile of them.

This needs `pull-requests: write`. `routine.yaml` already requires a
write-capable token in order to push its commits back, so this usually works
already; if the comment is the only thing failing, add the permission to your
caller workflow:

```yaml
jobs:
  routine:
    permissions:
      contents: write
      pull-requests: write
    uses: rstudio/shiny-workflows/.github/workflows/routine.yaml@v1
```

A token without the permission produces a warning, not a failed job. Set
`comment: false` to turn the comment off.

## Warnings

The action warns, but does not fail, when a dependency cannot be found in
`node_modules`, does not declare a license in its `package.json`, or does not
ship a license file. Those cases need a human to sort out what the license
actually is.
